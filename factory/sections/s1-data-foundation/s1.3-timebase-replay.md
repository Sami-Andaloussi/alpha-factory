# S1.3 — Deterministic timebase, immutability & replay

## TL;DR

The factory's master tape: one immutable, append-only log of every event, in a single stable order.
Any interval can be rewound and replayed with bit-identical results, today or in a year.
Research, simulation, execution and monitoring all read the same tape.

## Purpose

Set up the factory's master tape: an immutable [event log](../../glossary.md#event-log), ordered
totally and stably by the [timebase](../../glossary.md#timebase), and [replayable](../../glossary.md#replay)
identically.

**Success looks like:**
- With strictly identical inputs, every computation (research, execution simulation and cost
  analysis, production) lands bit for bit on the same outputs, today as tomorrow.
- Any interval can be rewound, the order of its events proven, and every decision explained.

<details>
<summary><b>Constraints and service levels</b></summary>

**Constraints.**
- One [canonical order](../../glossary.md#canonical-order); no downstream module may define
  another.
- An explicit as-of date in every query on state.
- Canonical formats (stable serialisation), one reference timestamp in UTC, and zero tolerance
  for in-place updates.

**Service levels** (to calibrate):
- Append: p95 end-to-end latency under X seconds for critical events.
- Replay: a minimum throughput, in days of history per hour.
- Critical events (IPO, suspension, delisting): guaranteed T90 / [T95](../../glossary.md#t95) update times, with an alert
  when they are exceeded.

</details>

## Gates

**Entry.** Start only when:
- the canonical order rule is approved and its edge cases are covered;
- the event typology is settled and the bitemporal contract of S1.2 is operational;
- the first "gold" datasets, whose correct replay is known, are defined.

**Exit.** Verdict *pass* when all of these hold:
- 100% of the reference replays are bit-identical;
- the audit finds zero in-place update, and the chain of manifests is complete;
- the [KPIs](../../glossary.md#kpi) are green over 2 observation cycles.

*Retry* and *fail* follow the [gate verdict](../../glossary.md#gate-verdict) rule.

**Requalification.** Rerun the heavy tests when:
- a source, a [venue](../../glossary.md#venue) or a new type of event is added;
- the ordering or tie-break rule, the numerical precision or the serialisation changes;
- an integrity incident occurs (a hash mismatch), replay or ordering KPIs [drift](../../glossary.md#drift), or market rules
  change.

Monitoring (S6) ingests the KPIs and alerts and runs the escalation runbooks;
[incident response](../../glossary.md#incident-response) (S7.9) replays the log, through the replay
API of S1.8, to write its postmortems. Lifecycle (S7) sets the audit cadence and the
[requalification](../../glossary.md#requalification) thresholds, and owns the migration plan for
snapshots and segments and their deprecation policy.

## Steps

<details>
<summary><b>1 · Set the canonical order contract</b> — Design task</summary>

**Goal.** One ordering rule that settles every tie between events, without ambiguity, and
depends neither on chance nor on parallelism.

**Actions.**
- Formalise the times in play (event time, publication time, ingestion time) and choose the
  reference time for ordering.
- Write the tie-break rule, for example a composite key: reference timestamp, then the source's
  sequence number, then an internal ID, so that every tie is settled.
- Set the policy for concurrent events: a stable order decided by the rule, never by the order in
  which threads happen to arrive.
- Document time zones and conversions (UTC, daylight saving) and forbid any dependence on a local
  clock.

**KPI.** Order ambiguities: 0 per 10⁹ events; p95 time to settle a tie.

**Guardrail.** Fuzz tests on equal timestamps, injected collisions, and a check that the order
never depends on the ingestion pipeline.

**Output.** Canonical order specification, as a document and ground-truth tests → the immutable
log (step 2), multi-source synchronisation (S1.4), the replay API (step 4).

</details>

<details>
<summary><b>2 · Design the immutable log and the event model</b> — Design task</summary>

**Goal.** Record history without ever rewriting it.

**Actions.**
- Define a minimal event schema, with a normalised header (keys, reference time, source,
  version), and a clear typology: raw data, correction, cancellation, heartbeat, metadata
  change.
- Forbid in-place updates: every correction is a corrective event that points to the original,
  through the bitemporal link of S1.2.
- Cut the log into sealed segments, the units of rotation and operations, each with a
  [manifest](../../glossary.md#dataset-manifest): hash, time bounds, event count, dependencies.
- Set the [retention policy](../../glossary.md#retention-policy) (how many "hot" and "cold"
  segments), the rotation, and periodic integrity checks.

**KPI.** p95 append latency; share of corrective events properly flagged; segment integrity =
100%.

**Guardrail.** Sentinels against in-place updates; the manifest (hash, count, bounds) is checked
at every rotation.

**Output.** Append-only segments with sealed manifests, and a versioned event catalogue →
snapshots and deltas (step 3), the replay API (step 4), audit and monitoring (S6).

</details>

<details>
<summary><b>3 · Build snapshots and restart deltas</b> — Design task</summary>

**Goal.** Replay fast, without starting from zero and without losing determinism.

**Actions.**
- Define when and what to snapshot (the canonical state of the tables and views recorded by the
  timebase), and how to generate the deltas between two [snapshots](../../glossary.md#snapshot).
- Specify the invariants of a snapshot (closed in time, self-sufficient, signed) and the
  consistency test: the state rebuilt from zero equals the state rebuilt from a snapshot plus its
  deltas.
- Plan the frequency and spacing of snapshots, for example matched to the sources' throughput
  and to the needs of execution simulation and cost analysis.

**KPI.** Coverage, the share of time replayable from a snapshot; p95 time to start a replay from a
snapshot.

**Guardrail.** An equivalent-rebuild test, from zero versus from snapshot plus deltas, with a
tolerated gap of 0 bits.

**Output.** Snapshot and delta policy and pipeline, and sealed reference datasets → the replay
API (step 4), the strategy lab (S3), validation and execution simulation (S4).

</details>

<details>
<summary><b>4 · Specify the deterministic replay API</b> — Design task</summary>

**Goal.** Offer an as-of reading of the tape, in slow motion, real time or accelerated, with the
same bytes every time.

**Actions.**
- Define the supported requests: "replay from t0 to t1", "give me the state as of", "resume from
  this snapshot", "speed ×N", "honour or ignore heartbeats".
- Define the error contracts (a missing segment is an explicit failure, with proof), the
  handling of backpressure, and bounds on buffer size.
- Require strict modes: no system time, no random number without a [seed](../../glossary.md#seed),
  no uncontrolled reordering; expose a strict-reproducibility flag.

**KPI.** Bit-identical replays on the gold datasets = 100%; replay throughput, in days per hour.

**Guardrail.** The same replays run under different environments and speeds; any divergence
raises a blocking alert.

**Output.** The [replay API](../../glossary.md#replay-api) contract: specification, test sets,
edge cases → research (S3), execution simulation and cost analysis (S4), execution (S5),
monitoring (S6).

</details>

<details>
<summary><b>5 · Lock execution determinism</b> — Design task</summary>

**Goal.** Remove the invisible sources of randomness.

**Actions.**
- Fix every pseudo-random seed, forbid calls to the wall clock, and document the time unit and
  zone.
- Choose a compatible concurrency model: sequential application of the timebase, or strictly
  [deterministic](../../glossary.md#deterministic) parallelism.
- Normalise numerical tolerances (precision, rounding, order of reductions) and formats
  (canonical serialisation).

**KPI.** Non-deterministic artefacts detected per week = 0; coverage of the non-deterministic
points (random numbers, time) = 100%.

**Guardrail.** Static and dynamic analysis of the sources of non-determinism; multi-threaded and
sequential runs must be strictly equal.

**Output.** Deterministic execution rules and a cross-environment test harness (different
environments, same outputs) → every compute path (S3 to S5), monitoring (S6).

</details>

<details>
<summary><b>6 · Prove immutability and provenance</b> — Execution task</summary>

**Goal.** Be able to show that the tape has not moved.

**Actions.**
- Compute and publish the hashes of segments and snapshots, and verify the chain of manifests.
- Keep the register of versions (schemas, ordering rules, event typology) and link each run to
  the manifest it consumed.
- Prepare the audit procedures: independent rebuild, random checks, exportable proofs.

**KPI.** Hash mismatches = 0; p95 audit time.

**Guardrail.** Random sampling of segments for re-hashing; independent review.

**Output.** [Provenance registry](../../glossary.md#provenance-registry), integrity proofs and
audit procedures → governance (S1.8), compliance, postmortems (S7.9).

</details>

<details>
<summary><b>7 · Validate and operate: the control loop</b> — Execution task</summary>

**Goal.** Measure, detect, correct.

**Actions.**
- Build a panel of reference replays on the gold datasets and require regular bit-identical
  replays.
- Instrument the KPIs (latency, throughput, order), set thresholds and alerts, and an escalation
  plan.
- Feed these metrics into monitoring reports (S6) and lifecycle reviews (S7) for requalification.

**KPI.** [MTTD and MTTR](../../glossary.md#mttd-mttr) on ordering deviations; gold tests passed =
100%.

**Guardrail.** A safe-stop policy (graceful degradation) when a segment or snapshot is in doubt,
restarting from the last healthy point.

**Output.** Dashboard, recurring tests and operational [runbooks](../../glossary.md#runbook) →
monitoring (S6), lifecycle (S7), every downstream team.

</details>

## Deliverables

- Canonical order specification: tie-breaks, reference time, conversions.
- Event model (schema, typology, correction rules), rotation policy and documented manifests.
- Snapshot and delta procedure, and the first sealed snapshots.
- Replay API contract and its test sets: gold datasets, edge cases, non-regression.
- Determinism rules (seeds, time, parallelism, numerics) and a multi-environment harness.
- Provenance registry (versions, hashes, dependencies) and audit procedures.
- KPI dashboard and runbooks: incident, restart, requalification.
- Decision log: choices, trade-offs, reasons, impacts.
